Phase 9 implemented basic polling loop with exponential backoff for transient errors (Plan 02). This plan adds lifecycle behaviors: offline detection, auto-resume, and graceful shutdown.

User decisions:
- Offline detection: Match official listener's detection logic exactly
- Reconnection strategy: Exponential backoff (start 1s, double each retry up to max ~60s)
- Stream ended behavior: Automatically discover next stream on that channel (seamless for 24/7 streamers)
- Graceful shutdown: Complete within 25-second timeout, force exit immediately if cleanup exceeds 25s

This plan is independent of all other plans (no dependencies) - enhances the existing Phase 9 poller. Can run in parallel with Plans 01, 02, 03 as Wave 1.

  <action>
Create poller/lifecycle.go with lifecycle management functions:

1. DetectOffline(resp *innertube.LiveChatResponse) bool function:
   - Check if response.ContinuationContents.LiveChatContinuation.Continuations is empty
   - Empty continuations = stream ended
   - Return true if offline, false if live

2. HandleStreamOffline(channelID string, repository *Repository, logger *zap.Logger) function:
   - Log offline detection with channel_id and video_id fields
   - Delete Redis mapping: repository.DeleteChannelVideoMapping(ctx, channelID)
   - Return error to trigger manager's discovery loop restart

3. StartDiscoveryLoop(ctx, channelID string, discovery *Discovery, repository *Repository, logger *zap.Logger) function:
   - Background loop: poll for new stream with exponential backoff (1m → 2m → 5m → 10m)
   - Continue as long as context not cancelled
   - On discovery success: persist to Redis, return video ID
   - On discovery failure: backoff and retry
   - Used by manager when stream ends and channel still has connected overlays

Create lifecycle_test.go:
- TestDetectOffline_EmptyContinuation (returns true)
- TestDetectOffline_ValidContinuation (returns false)
- TestHandleStreamOffline_DeletesMapping (verifies Redis deletion)
- TestStartDiscoveryLoop_Success (discovers new stream)
- TestStartDiscoveryLoop_Timeout (gives up after max attempts)

Why auto-resume: User decision - 24/7 streamers need seamless recovery. Manual restart NOT acceptable for production. Discovery loop runs until either new stream found or all overlays disconnect.
