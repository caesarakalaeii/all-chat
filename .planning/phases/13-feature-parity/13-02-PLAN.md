<objective>
Implement per-channel deletion event buffering to handle race conditions where deletion events arrive before the original message reaches the message-processor.

Purpose: InnerTube emits deletion events immediately, but there's no guarantee the original message has been processed by message-processor and stored in the registry. A 500ms buffer delay ensures the original message is indexed before the deletion event arrives, preventing "deletion of unknown message" errors.

Output: DeletionBuffer package with per-channel circular buffers (container/ring), 500ms flush interval, FIFO overflow strategy (max 1000 events), and integration with Redis publisher.
</objective>

Create `deletion/buffer.go` package implementing per-channel deletion buffering:

**Core Types:**
```go
type DeletionBuffer struct {
    bufferDuration time.Duration                      // Fixed 500ms delay
    maxSize        int                                 // Fixed 1000 events per buffer
    channels       map[string]*channelBuffer           // Per-channel buffers
    publisher      Publisher                           // Interface for testing
    mu             sync.RWMutex                        // Protect channels map
    logger         *zap.Logger                         // Structured logging
}

type channelBuffer struct {
    ring     *ring.Ring                               // Circular buffer (stdlib container/ring)
    ticker   *time.Ticker                             // 100ms flush check interval
    stopChan chan struct{}                            // Graceful shutdown
}

type bufferedEvent struct {
    message   *innertube.RawChatMessage               // Deletion event to emit
    addedAt   time.Time                               // When added to buffer
}

type Publisher interface {                            // For testing
    Publish(msg *innertube.RawChatMessage) error
}
```

**Key Methods:**
- `NewDeletionBuffer(publisher Publisher, logger *zap.Logger) *DeletionBuffer`: Initialize with 500ms delay, 1000 max size
- `Add(channelID string, deletionEvent *RawChatMessage) error`: Add event to channel's buffer, create buffer if needed, drop oldest if full
- `flushExpired(channelID string) error`: Check ring for events older than 500ms, publish via publisher, remove from ring
- `Cleanup(channelID string)`: Stop ticker, flush remaining events, remove buffer (prevent memory leak)
- `startFlusher(channelID string)`: Goroutine that runs 100ms ticker calling flushExpired

**Implementation Details:**

1. **Circular Buffer (container/ring):**
   - Use `ring.New(maxSize)` for fixed-size circular buffer
   - On Add: `ring.Value = bufferedEvent{message, time.Now()}`
   - On overflow: `ring = ring.Next()` (automatically overwrites oldest, FIFO per user decision)
   - Zero allocations after initialization (ring reuses slots)

2. **Time-based Flushing:**
   - Each channel has 100ms ticker (5x per buffer window for responsiveness)
   - On tick: Walk ring, check `time.Since(addedAt) >= 500ms`
   - Publish expired events, set `ring.Value = nil` (mark as flushed)
   - Stop walking when first non-expired event found (ring is time-ordered)

3. **Per-channel Isolation:**
   - Separate buffer per channel prevents cross-channel blocking
   - Channel goes offline → Cleanup() flushes remaining events → removes buffer
   - New channel → lazy initialization on first Add()

4. **Publisher Integration:**
   - Accept `Publisher` interface (not concrete *StreamPublisher) for testability
   - Call `publisher.Publish(deletionEvent)` for each expired event
   - Log errors but continue flushing (eventual consistency per user decision)

5. **Overflow Strategy:**
   - User decision: Drop oldest (FIFO) when buffer full
   - Log warning: `log.Warn("Deletion buffer overflow", zap.String("channel_id", channelID), zap.Int("dropped", 1))`
   - Metrics: Track overflow count (Task 2)

6. **Edge Cases:**
   - Buffer full: Overwrite oldest slot, log warning
   - Flush during Add: Protected by mutex, ring is thread-safe
   - Publisher.Publish error: Log error, continue flushing (drop event per eventual consistency)
   - Cleanup during flush: Stop ticker first, flush synchronously, then remove

**Timing Coordination (Claude's discretion per CONTEXT.md):**
Research question: "How do 100ms batch detection and 500ms buffer delay coordinate?"
**Solution:** Batch detector emits metadata immediately after 100ms window closes → Buffer adds event with current timestamp → Buffer flushes 500ms later. Total delay: 100ms (detection) + 500ms (buffer) = 600ms from first deletion to emission.

**What NOT to do:**
- Do NOT use time.Sleep for delays (use ticker for testability)
- Do NOT sort buffer by timestamp (ring preserves insertion order, sufficient per user decision)
- Do NOT retry on publisher failure (drop and log per eventual consistency)
