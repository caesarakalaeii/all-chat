  <files>shared/coordination/client.go</files>
  <action>
Create `shared/coordination/client.go` with HTTP client for coordinator integration.

**CoordinatorClient struct:**
- `baseURL string` - Coordinator service URL (e.g., "http://source-manager:8088")
- `serviceJWT string` - JWT token for SERVICE_JWT_AUTH
- `httpClient *http.Client` - HTTP client with 10s timeout
- `logger *zap.Logger`

**Methods:**

1. **NewCoordinatorClient(baseURL, serviceJWT string, logger *zap.Logger) *CoordinatorClient**
   - Initialize HTTP client with 10s timeout
   - Return configured client

2. **QueryAssignments(ctx context.Context, podID string) ([]*Assignment, error)**
   - Implements TWITCH-01, KICK-01, TIKTOK-01
   - URL: `GET {baseURL}/assignments?pod_id={podID}`
   - Add Authorization header: `Bearer {serviceJWT}`
   - Retry with exponential backoff (1s, 2s, 4s, 8s, 16s, 30s max) on connection errors
   - Block indefinitely until coordinator responds (per CONTEXT.md user decision)
   - Parse JSON response into Assignment slice
   - Return assignments or error

3. **PublishHeartbeat(ctx context.Context, podID string) error**
   - URL: `POST {baseURL}/heartbeat`
   - Body: `{"pod_id": "{podID}"}`
   - Add Authorization header: `Bearer {serviceJWT}`
   - Return nil on 200, error otherwise
   - Use existing Phase 5 HeartbeatRequest model structure

**Assignment struct** (matches source-manager models.Assignment):
```go
type Assignment struct {
    SourceID  string    `json:"source_id"`
    PodID     string    `json:"pod_id"`
    Timestamp time.Time `json:"timestamp"`
    Version   int       `json:"version"`
}
```

**Error handling:**
- Network errors → retry with backoff (coordinator might be starting)
- 400/500 errors → log and return error (configuration issue)
- All errors logged with zap.Logger

**Why blocking indefinitely:** Per CONTEXT.md user decision: "Block indefinitely until coordinator responds (pod not ready until assignments received)". Coordinator availability is critical for pod startup.

<task type="auto">
  <name>Task 2: Create MigrationSubscriber for Redis Pub/Sub migration event handling</name>
  <files>shared/coordination/migration_subscriber.go</files>
  <action>
Create `shared/coordination/migration_subscriber.go` with Redis Pub/Sub subscriber for migration events.

**MigrationSubscriber struct:**
- `redisClient *redis.Client` - Redis client from go-redis/v9
- `logger *zap.Logger`
- `handler func(*MigrationEvent)` - Callback for migration events

**Methods:**

1. **NewMigrationSubscriber(redisClient *redis.Client, handler func(*MigrationEvent), logger *zap.Logger) *MigrationSubscriber**
   - Store redisClient, handler, logger
   - Return configured subscriber

2. **Subscribe(ctx context.Context) error**
   - Implements MIGRATE-01 (overlap migration pattern notification)
   - Subscribe to Redis Pub/Sub channel: `migration:events`
   - Use existing pattern from `services/message-processor/publisher/pubsub_publisher.go`
   - Wait for subscription confirmation: `pubsub.Receive(ctx)`
   - Start goroutine to consume messages from `pubsub.Channel()`
   - For each message:
     - Unmarshal JSON payload into MigrationEvent
     - Log received event with migration_id, channel_id, from_pod, to_pod
     - Call handler callback with parsed event
     - Log errors but continue consuming (don't crash on malformed events)
   - Return when context canceled or subscription fails

**Error handling:**
- Subscription failure → return error (caller retries)
- Unmarshal errors → log warning, skip event, continue consuming
- Handler panics → recover, log error, continue consuming

**Why Redis Pub/Sub:** Per CONTEXT.md user decision: "Hybrid Redis Pub/Sub approach - Coordinator publishes migration event to Redis Pub/Sub channel (5-20ms latency) - All listener pods subscribe to `migration:events` channel - Faster than polling (15s avg), safer than direct HTTP push"

```go
}
```

Used by listeners to confirm successful connection during overlap protocol.

```go
type MigrationConfirmation struct {
```
