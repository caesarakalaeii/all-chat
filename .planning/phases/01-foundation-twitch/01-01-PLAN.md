  <action>
Create new `registry/` package in message-processor service implementing unidirectional mapping (platform ID → internal UUID).

**registry.go:**
- Define `MessageIDRegistry` interface with methods:
  - `Add(ctx, platform, channelID, platformMsgID, internalUUID string) error`
  - `Lookup(ctx, platform, channelID, platformMsgID string) (string, error)`
  - `Remove(ctx, platform, channelID, platformMsgID string) error` (for testing/cleanup)
- Implement `RedisRegistry` struct with:
  - `client *redis.Client` field
  - `ttl time.Duration` field (set to 1 hour per user decision)
- Use Redis hash structure: `msgid:registry:{platform}:{channelID}` as key, platform message IDs as fields
- Store value as `{internalUUID}|{timestamp}` format for debugging
- Use pipeline for atomicity: `HSET` + `EXPIRE` in single transaction to refresh TTL on each add
- Return `ErrMessageNotFound` (custom error) when HGET returns redis.Nil
- Extract UUID from stored value by splitting on pipe character

**registry_test.go:**
- Use miniredis (github.com/alicebob/miniredis/v2) for in-memory Redis testing
- Test cases:
  - Add message ID and lookup successfully returns UUID
  - Lookup non-existent message returns ErrMessageNotFound
  - TTL is set correctly on add (verify with TTL command)
  - Multiple channels don't conflict (different hash keys)
  - Same platform message ID in different channels stored separately
  - Pipeline atomicity (HSET + EXPIRE both succeed or fail)

**Implementation notes:**
- Use unidirectional mapping (platform ID → UUID only) per research recommendation
- Do NOT implement bidirectional mapping - deletion events always provide platform ID
- Key format allows per-channel isolation: `msgid:registry:twitch:shroud`
- Refresh TTL on every add to handle long-lived active channels
- Per CONTEXT.md: TTL is 1 hour (NOT 24 hours from requirements)
