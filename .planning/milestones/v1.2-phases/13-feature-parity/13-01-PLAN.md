<objective>
Implement time-windowed batch deletion detection to distinguish between single message deletions and batch moderation events (bans/timeouts).

Purpose: InnerTube provides individual deletion events, but moderator actions (ban/timeout) result in multiple deletions within milliseconds. Detecting this pattern allows us to synthesize a single "batch" event, reducing noise and enabling better moderation analytics.

Output: BatchDetector package with 100ms time-windowed aggregation, configurable threshold (default 5), and dual emission (batch events when threshold reached, single events otherwise).
</objective>

Create `deletion/batch_detector.go` package implementing time-windowed batch detection:

**Core Types:**
```go
type BatchDetector struct {
    threshold      int                          // Configurable threshold (default 5)
    windowDuration time.Duration                // Fixed 100ms detection window
    channels       map[string]*channelWindow    // Per-channel state isolation
    mu             sync.RWMutex                 // Protect channels map
}

type channelWindow struct {
    deletions []deletionEvent                   // Deletions in current window
    windowStart time.Time                       // Current window start time
    ticker    *time.Ticker                      // 100ms ticker for window boundaries
}

type deletionEvent struct {
    targetItemID string
    timestamp    time.Time
}
```

**Key Methods:**
- `NewBatchDetector(threshold int) *BatchDetector`: Initialize with configurable threshold (default 5 if threshold <= 0)
- `AddDeletion(channelID, targetItemID string, timestamp time.Time) (*batchResult, error)`: Add deletion to current window, return nil (buffering) or result if window closes
- `processWindow(channelID string) *batchResult`: Close current window, analyze deletion count, return batch or single event metadata
- `Cleanup(channelID string)`: Remove channel state when stream stops (prevent memory leak)

**Implementation Details:**
1. **Per-channel isolation**: Use `map[channelID]*channelWindow` to prevent cross-channel interference
2. **Window management**: Each channel has 100ms ticker. On tick, call `processWindow()` to analyze buffered deletions
3. **Batch detection logic**: If `len(deletions) >= threshold`, return `{isBatch: true, count: len(deletions)}`. Otherwise return `{isBatch: false, count: 1}` for each deletion
4. **Emission timing**: User decision specifies immediate emission after 100ms window. Detector returns metadata, caller (Plan 13-02 buffer) adds 500ms delay
5. **Reason detection**: Use deletion count heuristic per research: >=5 deletions = "timeout", >=20 = "ban", else "mod". Store in `reason` field
6. **Thread safety**: Use sync.RWMutex for channels map (RLock for reads, Lock for writes/cleanup)

**Edge Cases:**
- Deletions spanning multiple windows (e.g., 3 at t=0, 2 at t=150ms): Handle per user discretion - each window analyzed independently, no cross-window aggregation
- Empty windows: No-op, don't emit events for windows with zero deletions
- Concurrent AddDeletion calls: Protected by mutex, order preserved by timestamp
- Cleanup during active window: Stop ticker, process final window, remove from map

**Follow established patterns from Phase 12:**
- Error handling: Return error, log with zap (not panic)
- Naming: camelCase unexported, PascalCase exported
- Testing: Use time.Ticker with deterministic time for tests (not time.Sleep)

**What NOT to do:**
- Do NOT emit events directly (detector produces metadata, caller handles emission)
- Do NOT integrate with Redis/publisher yet (Plan 13-02 handles buffer + emission)
- Do NOT add metrics yet (Plan 13-03 handles metrics)
