## What is solid (verified — do NOT redo)

These were re-derived from scratch and confirmed correct/complete on the current HEAD:

- **B1 (cross-tenant IDOR):** every guarded owner UPDATE (`ClosePoll` polls.go:191, `LockPrediction` predictions.go:184, `ResolvePrediction` predictions.go:307, `CancelPrediction` predictions.go:354) carries `AND overlay_id = $N`; the 0-row path routes through `GetPollForOverlay`/`GetPredictionForOverlay` → `ErrNotFound` → 404 with no existence oracle. `TestB1_*` assert both the 404 **and** the round-unchanged invariant.
- **H1 (cross-economy wager):** `Wager` re-reads `overlay_id … FOR UPDATE` and rejects `rowOverlayID != overlayID` before any debit (predictions.go:206-221); `RecordVote` mirrors the guard (polls.go:225). Debit economy always equals credit economy.
- **H2/H3 (consumer durability):** `handle()` returns non-nil only on transient DB errors and nil on bad JSON / business rejections; `Run` acks conditionally; `drainPEL` uses group-wide `XAutoClaim` (MinIdle 5m) over both streams at startup + on a 60s ticker; `safeHandle` wraps `recover()` + a 5s deadline.
- **Payout math:** `ComputePayouts` is conservation-exact (`sum(credits) == sum(stakes)`) in every edge case attacked — zero-losers, zero-winners (refund-all), single winner, all-equal stakes, one-sided pool, empty input; remainder is provably `0 ≤ r < winnerCount`; the remainder recipient is a deterministic total order (stake desc, then ViewerID asc); double-resolve is a guarded 0-row no-op backstopped by the `payout:PID:VIEWER` dedup key.
- **Currency isolation is structural:** `source='twitch_native'` rows never set the active flag, never touch `viewer_points`; active-round uniques are `… AND source='allchat'`; the mirror idempotency index is `(overlay_id, source, external_id) WHERE external_id IS NOT NULL` and allchat rows always insert `external_id = NULL`.
- **Native-mirror monotonicity:** state-rank guard + `GREATEST` tallies + `COALESCE` timestamps + the L-C1 terminal-absorbing clause are correct and symmetric (RESOLVED↔CANCELED lateral flips blocked).
- **Earn-tier bugfix:** `subTier` keys off the real plan string (`1000/2000/3000/Prime`), not the display tier; `earn_test.go` proves Tier1/Prime→low and Tier3→high. Config guards (`validateEarnConfig` + migration 073 CHECKs + engine 1e12 clamp) block minting via absurd/negative/overflow multipliers.
- **Watch-point farming is clamped:** both heartbeat paths derive the dedup bucket from server wall-time (`time.Now().Unix()/60`) into the globally-unique `dedup_key`, so a viewer mints at most `WatchPerMinute` per real minute per overlay and cannot double-earn across the two heartbeat endpoints.
- **Token-type confusion impossible:** `shared/middleware/auth.go` sets `viewer_id` xor `user_id`; `requireUser`/`requireViewer` gate on those exclusively — a viewer JWT cannot drive an owner route.
- **Frontend participate a11y/XSS:** M-A1 dark tokens, M-A2 live regions (`role="alert"`, `aria-live`, `role="status"`), M-A3 tally contrast all landed; all dynamic values render through JSX text interpolation (no `dangerouslySetInnerHTML`/`innerHTML`); heartbeat interval re-keys on `[authed, id]` so it does not leak across an in-tab overlay switch; 401 → `setAuthed(false)`/login.

## P0 — BLOCKER (must fix before merge)

### P0-1. Migration re-run rebuilds global-unique indexes that later migrations rescope → platform-wide init-container crash-loop once real data exists
- **Severity:** critical · **Confidence:** high (reproduced firsthand against the SQL + runner) · **New** (missed by all prior passes)
- **Where:** `migrations/069_engagement_polls.sql:22,50`, `migrations/070_engagement_predictions.sql:25,68`; rescoped by `migrations/071_engagement_native_mirror.sql:15-21` and `migrations/072_engagement_dedup_scope_and_announce.sql:22-28`; runner `scripts/run-migrations.sh:86,107`.
- **Root cause:** the runner globs and re-runs **every** up-migration on every pod start under `ON_ERROR_STOP=1`, with no applied-migrations table (see memory `reference_migration_runner_reruns_all`). 069/070 create four **GLOBAL UNIQUE** indexes — `uniq_poll_source_external`/`uniq_prediction_source_external` on `(source, external_id)` and `uniq_poll_vote_msg`/`uniq_pred_entry_msg` on `source_message_id`. 071 drops the first pair and rescopes to `(overlay_id, source, external_id)`; 072 drops the second pair and rescopes to `(poll_id|prediction_id, source_message_id)` — both migrations' headers state the global scope is *wrong* because one Twitch round / one chat message legitimately fans out to N overlays sharing those values. On a **fresh** DB this sequence is fine (no data to collide), which is exactly why the "3× on fresh Postgres" check passed. But after the feature runs in production and a native round fans to ≥2 overlays (or a chat vote lands on ≥2 overlays), duplicate `(source, external_id)` / `source_message_id` rows exist. The next restart replays 069/070; `CREATE UNIQUE INDEX IF NOT EXISTS uniq_poll_source_external` does **not** short-circuit (071 dropped that name last run), so it rebuilds a global unique over duplicate data → `duplicate key value violates unique constraint` → `ON_ERROR_STOP` aborts the batch **before** 071/072 can rescope. The migration init-container exits non-zero and gates ~7 deployments → total inability to start/restart/deploy until manual DB surgery.
- **Trigger:** any pod restart (kured reboot, rolling deploy, HPA scale, OOM) after ≥1 native round or chat vote has fanned to ≥2 overlays — an essentially guaranteed steady-state condition, not an edge case.
- **Fix:** these are unreleased migrations in the same PR, so edit **069/070 in place** to create the **per-overlay / per-round** unique indexes directly (`ON polls(overlay_id, source, external_id)`, `ON poll_votes(poll_id, source_message_id)`, and the two prediction analogues), and remove the DROP/CREATE churn for those four indexes from 071/072 (071/072 then only add the `LOWER(channel_id)` functional index, `announce_on_start`, etc.). Keep an idempotent `DROP INDEX IF EXISTS <old_global_name>` in 071/072 as a no-op safety net for any dev/staging DB that already applied the branch's old 069/070. **All four indexes** need this — the finder first spotted only the `(source, external_id)` pair; the `source_message_id` pair rescoped by 072 has the identical bug.
- **Test:** a migration re-run regression — apply the full batch, insert a cross-overlay duplicate row for each of the four rescoped indexes, re-apply the full batch, assert it succeeds. This is the check the fresh-DB verification can't provide.

## P1 — HIGH (fix before merge / before GA)

### P1-1. Command + native consumers never recover from `NOGROUP` after a Redis reset / HA cutover
- **Severity:** high · **Confidence:** high · **New**
- **Where:** `services/engagement-service/consumer/command.go:90`, `consumer/native.go:83`; contrast `services/message-processor/consumer/stream_consumer.go:201-209`.
- **Root cause:** both consumers call `XGroupCreateMkStream` once at the top of `Run`, then treat every `XReadGroup` error identically (`log.Warn` + `continue`). There is no `NOGROUP` branch. Producers reach the streams via `XADD`, which recreates the **stream** after a Redis data loss but **not** the consumer **group**. After a full HA cutover / Redis reset to an empty instance (documented as real in this cluster — memory `project_redis_outage_cascade_discord_flapping`), `XReadGroup` returns `NOGROUP` forever; the loop spins logging Warn while every chat vote/wager and every Twitch-native lifecycle event is **silently dropped** until the pod is manually restarted. `/health/ready` only pings Postgres, so the pod stays Ready and k8s never restarts it. This defeats the exact durability guarantee H2/H3 were added to provide.
- **Fix:** in both `Run` loops, detect `strings.Contains(err.Error(), "NOGROUP")` and re-run `XGroupCreateMkStream` (ignoring `BUSYGROUP`) before continuing, mirroring `stream_consumer.go`. This also covers a transient boot-time group-create failure. Consider adding Redis to the readiness probe. **Caveat:** recreating at `$` still loses messages `XADD`ed during the group-absent window; the fix restores forward self-heal, not the outage-window gap.
- **Test:** add to the H1/H3 integration suite — drop the consumer group under a live stream, push a message, assert the consumer recreates the group and processes it.

## P2 — MEDIUM (fix before GA)

### P2-1. Redelivered chat wager/vote re-targets the *currently* active round → double-debit on a round the viewer never chose
- **Where:** `consumer/command.go:195` (re-resolves `GetActivePrediction` per delivery); dedup is round-scoped (`(prediction_id, viewer_id)` PK + `(prediction_id, source_message_id)` index + `wager:PID:VIEWER` ledger key).
- **Root cause:** a transient DB error / ambiguous `tx.Commit` leaves the entry pending; `periodicDrain` reclaims it after 5m. If the original round resolved and a **new** round opened on that overlay in between, the redelivery resolves to the new round and applies a **fresh real debit**. The ambiguous-commit variant double-debits the viewer (P1 committed server-side, client retried onto P2). Points stay conserved system-wide, but the individual viewer loses points to a wager they never made.
- **Fix:** make replay-dedup **round-independent** — an overlay-scoped ledger dedup key `wager:<overlayID>:<source_message_id>` (+ matching `(overlay_id, source_message_id)` uniqueness on entries). This preserves the ADR-0028 one-message→N-overlay fan-out (the key includes `overlay_id`). **Fall back to the Redis stream entry id (`msg.ID`)** as the dedup token for non-UUID platforms, whose `source_message_id` is currently `nil` (`parseUUIDOrNil`, command.go:278) and therefore skip the guard entirely today.

### P2-2. Gate-arm failure at round open silently kills chat participation for the whole round
- **Where:** `handler/poll.go:92,191-197`, `handler/prediction.go` (analogue), `publisher/publisher.go:97-111`.
- **Root cause:** `CreatePoll` commits + broadcasts the round **before and independently of** arming the message-processor hot-path gate; `markActive`/`SetActive` only `log.Warn` on Redis failure. A transient Redis blip during create leaves the round live and visible while the `engagement:active:{platform}:{channel}` SET is never written → message-processor reads `EXISTS==0` forever and drops every command-shaped vote, counted only as `result="miss"` (indistinguishable from a poll nobody voted on). Nothing re-arms it; the 24h TTL self-heal doesn't apply because the key was never created.
- **Fix:** add a periodic **reconciler** in `runSweeper` that re-derives active flags for all live All-Chat rounds and re-`SetActive`s them (restart-safe; mirrors the DB-is-source-of-truth auto-lock/close pattern), plus a `SetActive`-failure counter so a never-armed gate is observable. This also covers the sub-ms commit→markActive race.

### P2-3. Viewer participate page opens the owner `/ws/overlay` socket → source auto-activation + YouTube quota polling driven by viewers + unbounded reconnect storm
- **Where:** `frontend/src/lib/hooks/useEngagementLive.ts:48` (`client.connect(overlayId, null, true)`), mounted on `frontend/src/app/overlay/[id]/participate/page.tsx:180`; gateway `services/api-gateway/handlers/websocket.go:230-234,247-249,267`.
- **Root cause:** the engagement live-signal hook uses the **owner/OBS** endpoint `/ws/overlay/{id}` with no token → anonymous "obs" mode → `ActivateSourcesForOverlay` (writes `is_active=true`, sustains demand-based YouTube polling — the exact thing `/ws/chat` `SubscribeViewerOnly` was built to avoid). A shared participate URL means every viewer tab activates sources and amplifies YouTube quota (a documented-sensitive resource) with no owner in the loop; when the overlay is inactive the gateway 403s and the client reconnect-loops forever (`websocket.ts:259-272` only stops on explicit `disconnect()`).
- **Fix:** add a public, side-effect-free engagement WS endpoint (or an `engagementOnly` query flag consumed by `HandleOverlayConnection`) that broadcasts only `poll_update`/`prediction_update` and skips `ActivateSourcesForOverlay` + YouTube polling; point `useEngagementLive` at it. Or drop the WS accelerator on participate and rely on the 3s HTTP poll (L-D1 already documents the WS path as an unused nicety). **At minimum**, cap reconnect attempts / stop on a non-101 handshake so an inactive overlay doesn't reconnect-storm from every viewer tab.

### P2-4. Native stale-sweep force-cancels a legitimately LOCKED Twitch prediction, then the terminal-absorbing guard permanently drops the real resolution
- **Where:** `services/engagement-service/repository/native.go:237` (`ForceCloseStaleNativePredictions`), guard at `native.go:130-132`, sweeper at `cmd/main.go:285,325-327`.
- **Root cause:** the 4h stale sweep cancels any `twitch_native` prediction still ACTIVE/LOCKED past the TTL, on the false premise that Twitch rounds resolve within ~30m — only the *betting window* is capped; a LOCKED prediction has no forced-resolution deadline. Once the sweep sets CANCELED, the genuine `channel.prediction.end` RESOLVED event is blocked by the L-C1 terminal-absorbing guard and silently dropped; the overlay shows CANCELED with no winner forever. Display-only (native rounds carry no points), but a permanently wrong on-stream result.
- **Fix:** mark sweep-originated cancels distinctly (e.g. `force_closed` / `origin='sweep'`) and relax the absorbing guard to let a later genuine Twitch terminal override a **synthetic** CANCELED for `source='twitch_native'` only — keeping the RESOLVED→CANCELED direction of the L-C1 guard intact. (Alternatively drive the sweep off `locked_at` with a much longer, Twitch-aligned bound.)

### P2-5. `"+1"` chat-agreement idiom is silently counted as a poll vote
- **Where:** `consumer/command.go:267-271` (bare-number shortcut), pre-filter `message-processor/consumer/engagement.go:129-132`.
- **Root cause:** `strconv.Atoi` accepts a leading sign, so `"+1"…"+99"` parse as votes for that option. `"+1"` is one of the most common chat-agreement idioms; with `allow_change` default-on, a viewer typing `+1` then `+2` silently re-votes. Distinct from the accepted M7 "bare numbers count as votes" tradeoff. Poll-tally only (no points).
- **Fix:** gate the bare-number shortcut (and the pre-filter) on ASCII-digits-only before `Atoi` (reject a leading `+`/`-`, or match `^[0-9]{1,2}$`). Add `"+1"`/`"+2"`/`"-1"` → `cmdNone` cases to `TestParseCommand`.

### P2-6. H2/H3 merge-gate consumer semantics have zero automated test coverage
- **Where:** `consumer/command_test.go` (only `TestParseCommand`), `consumer/native_test.go` (only pure mappers).
- **Root cause:** the two highest-risk consumer changes (conditional ack; `XAutoClaim` drain) are asserted nowhere — a refactor re-introducing unconditional `XAck` or swallowing the DB error ships green. `miniredis/v2` is already vendored.
- **Fix:** consumer-level tests — (a) a repo-erroring message stays in the PEL (not acked); (b) malformed JSON **is** acked; (c) an idle PEL entry under a dead consumer name is reclaimed by `drainPEL` (`mr.FastForward` past the 5m min-idle, or gate behind the integration tag against real Redis).

## P3 — LOW / nit (backlog; do not gate merge)

- **P3-1. `071_engagement_native_mirror_down.sql:6` recreates the global-unique `(source, external_id)` index** — the identical landmine to P0-1 on the manual rollback path; followups #3 only fixed the `source_message_id` down-path in 072. Recreate non-unique (like 072_down), and wrap the down statements in `BEGIN/COMMIT` so a failed recreate doesn't leave the mirror path with no dedup index. *(medium-ish, but rollback-only → parked at P3.)*
- **P3-2. Migration-number drift** (reported by 7 lenses): `docs/plans/pr-524-followups.md:11`, the deploy runbook, and code comments (`consumer/command.go:171`, `repository/repository.go:148`) call the dedup-rescope/`LOWER(channel_id)`/`announce_on_start` work "migration 071". It is actually **072** (071 is native_mirror). Runtime-harmless (runner globs by number), but the deploy checklist verifies the wrong file. Fix all references to 072/073.
- **P3-3. Reclaimed stale poll vote reverts a viewer's newer vote change** (`repository/polls.go:248`): `RecordVote`'s `ON CONFLICT … DO UPDATE` has no ordering guard, so a 5m-drained redelivery re-applies the old option. Thread a monotonic key (Redis stream entry id / chat timestamp) onto `poll_votes` and guard `WHERE EXCLUDED.seq >= poll_votes.seq`. Tally-only.
- **P3-4. `is_public_for_viewers` enforced only on the streamer-keyed path, not the direct overlay-id endpoints** (`handler/poll.go:152`, `prediction.go:206`, `points.go`): the overlay UUID is a durable capability (embedded in the shared participate URL), so `WebVote`/`WebWager`/`GetBalance`/`GetEngagement`/`Heartbeat` keep working after a streamer toggles public-for-viewers off, diverging from the chat-WS gate. No cross-tenant leak / no theft. Add an `OverlayPublicForViewers(overlayID)` predicate to those handlers, **or** document the capability model explicitly in ADR-0031.
- **P3-5. Forwarder goroutine: no `recover()` + abandons its buffer on shutdown** (`message-processor/consumer/engagement.go:57`): a rolling deploy during a live poll silently drops up to 1024 already-acked vote candidates (only the buffer-**full** case is counted). Add a shutdown best-effort drain / distinct `"abandoned"` metric label, and a `defer recover()` mirroring earn.go `safely()`.
- **P3-6. No byte-size cap on forwarded command text** (`message-processor/consumer/engagement.go:120`): `looksLikeCommand` bounds neither length; a multi-KB `!`-prefixed payload is XADDed verbatim (stream is entry-count-capped, not byte-capped). Reject/truncate candidates over ~200-500 bytes.
- **P3-7. Earn-event republish is synchronous on the consume loop** (`message-processor/cmd/main.go:708`): inconsistent with the L-Perf1 async command-forward hand-off; a gift-sub/raid burst runs N synchronous `engagement:events` publishes per event on the single consume goroutine. Route through the same bounded async hand-off (drop-and-count on full; earn is already best-effort).
- **P3-8. Payout idempotency + unequal-stake remainder are unit-tested only on the pure engine** (`engine/payout_test.go:73`): the remainder test uses equal stakes (exercises only the UUID tie-break, not "remainder to largest stake"), and no test calls `ResolvePrediction`/`CancelPrediction` **twice** to prove the ledger dedup-key backstop. Add an unequal-stake/odd-pool engine test + an integration test asserting per-winner balances, whole-economy conservation, and double-resolve/double-cancel no-op.
- **P3-9. Monitor control panel clears an ACTIVE round on any non-404 error** (`EngagementControls.tsx:198-203`): a transient 5xx blanks the owner's live round (the OBS widget correctly distinguishes 404). Treat only 404 as "no round" on both the poll and prediction branches.
- **P3-10. Internal announce is an arbitrary-message-as-any-streamer primitive gated only by the shared service-JWT secret** (`auth-service/handlers/chat_announce.go:57`): not externally reachable, consistent with the trust model, but a wider internal surface than `/chat/send` (acting streamer comes from an unauthenticated body field). Document in the security residuals; keep the NetworkPolicy allow-list to `auth-service:8081/internal` tight; consider a dedicated engagement-only key/kid.
- **P3-11. M2 "settled" banner skipped on a fast round-to-round handoff** (`participate/page.tsx:144`): raise the settled banner for the remembered round before adopting the new one. Deferred-M2 scope.
- **P3-12. Poll OBS widget declares a single "Winner" on a vote tie** (`poll/page.tsx:88`): `find` returns the first max; compute the max-set and show "Tie" (or suppress the highlight) when not unique.
- **P3-13. Shutdown does not await background goroutines before closing the DB pool / Redis client** (`cmd/main.go:215`): spurious "closed pool" logs on SIGTERM; no data loss (ops are redelivery-safe). Add a `sync.WaitGroup` over the four consumers + sweeper + `periodicDrain` and a bounded `wg.Wait()` after `srv.Shutdown()`.
- **P3-14. `IsUserPremium` (`repository.go:126`) is dead code** — no handler enforces a premium gate on engagement owner routes. If engagement is meant to be premium-only, that gate is currently unenforced backend-side (plausibly deferred to the feature-gate phase); confirm intent.
