# Frontend i18n

UI strings live in a typed catalog at `frontend/src/lib/i18n/`. English is
the default and source locale, German is the second. The user picks the
language in the homepage nav or on `/settings`; the choice is stored per
browser (`localStorage.allchat_locale`) and the locale never appears in the
URL (overlay links are pasted into OBS and must keep resolving). The design
decisions are in ADR-0055 (catalog), ADR-0066 (locale selection) and ADR-0078
(homepage switch); this guide is the practical part.

## Structure

- `config.ts`: `SUPPORTED_LOCALES`, `LOCALE_NATIVE_NAMES`, `isSupportedLocale`
- `messages/en/<namespace>.ts`: one file per surface-namespace, nested object
  literal ending in `as const` (load bearing: `MessageKey` is derived from the
  literal key types; do not annotate or spread the barrel)
- `messages/de/<namespace>.ts`: German files typed as the complete English
  shape, so a missing or extra key is a `tsc` error (`legal` is exempt)
- `translate.ts`, `active-locale.ts` (module-singleton active locale +
  `restoreStoredLocale`/`chooseLocale`), `translators.ts`,
  `use-translations.ts`, `format.ts` (`formatNumber`, `formatDateTime`),
  `index.ts` (what call sites import)

No React Context, no store library, no dependency. There is no namespace
called `en.ts`; importers write `./messages/en` and get the barrel.

Namespaces are keyed by the surface a reader can point at
(`dashboard`, `settings`, `overlayEditor`, ...). `common` is only for a string
genuinely shared by two or more surfaces; a new namespace must be added to
`EXPECTED_NAMESPACES` in `src/lib/i18n/__tests__/messages.test.ts`.

## Adding a string

1. Add the key to `messages/en/<namespace>.ts`.
2. Add the German string at the same path in `messages/de/` (compile error
   until you do).
3. Read it at the call site with

```tsx
const t = getTranslations()      // Server Components, modules, tests
const t = useTranslations()      // 'use client' components
t('maintenanceBanner.dismissLabel', { title: 'Database upgrade' })
```

Keys are dotted, max three levels deep, and checked at compile time: a typo
is a `tsc --noEmit` error. `getTranslations()` resolves the active locale on
each call (which is English on the server); `useTranslations()` re-renders on
language switches. `t` keeps one identity across switches, so effects do not
re-run on a switch, but a `useMemo` keyed on `t` freezes on whatever locale
was first.

Placeholders are `{name}`, matching `frontend/src/lib/errorMessages.ts`. Do
not concatenate translated fragments into sentences; put whole sentences in
one key. There are no ICU plurals: the `…One`/`…Many` key pairs cover the
English/German one/other split. A German string must keep exactly the
placeholders of its English source (`__tests__/de.test.ts` fails otherwise).

## Lookup never throws

A missing key in the active catalog resolves in English, then to the key
string; a missing param renders as `{placeholder}`; both `console.warn`
outside production. This is deliberate: overlay pages render in OBS on live
broadcasts, and a thrown exception unmounts the tree. Do not "improve" it.

## Lint gate

`frontend/eslint.i18n.config.mjs` fails on user-visible strings rendered
inline: JSX text nodes (`react/jsx-no-literals` with `noStrings: true`) and
the props `aria-label`, `placeholder`, `title`, `alt`, `label` (an empty
`alt` stays exempt). It runs in `.github/workflows/frontend-i18n.yml`. Run
locally exactly as CI does (`--suppressions-location
eslint.i18n.suppressions.json`). Punctuation is in `allowedStrings`; not
linted: stories, tests, blog posts (`src/content/blog/**`, dated prose, not
UI copy) and Stylebook; blog chrome is linted.

`frontend/eslint.i18n.suppressions.json` is a shrink-only baseline. After
migrating strings, prune with `--prune-suppressions` and commit the shrunken
file. Never run `--suppress-all`. There is no inline escape hatch:
`noInlineConfig: true` makes eslint-disable comments ineffective.

## Locale mechanics

The server always renders English (no cookie, header or account read; pages
stay static). `components/LocaleSync.tsx` in the root layout calls
`restoreStoredLocale()` after hydration, which loads the stored catalog with
a dynamic `import()` and activates it (`<html lang>`, subscribers re-render).
The homepage switch (`components/home/LanguageToggle.tsx`) and the settings
language card call `chooseLocale()`; no stored choice means English, never
the browser's language (an OBS instance on a German machine must not switch).

Stays English: Server Components and their metadata, `legal.*` everywhere
(binding text is not published in a language a lawyer has not read),
strings resolved once at module load, and overlays in OBS (separate storage).
The `/settings` card may be gated by the `ui_languages` feature gate via
share-service; the homepage switch is not gated (signed-out visitors could
never pass it).

Why there is no provider: the frontend has no React Context at all, and
Storybook requires every component to render standalone (a required CI
gate). The active locale is the module singleton; the hook subscribes with
`useSyncExternalStore`.

## Dates and numbers

Use `formatDateTime`/`formatNumber` from `@/lib/i18n`, not `toLocaleString()`
or a bare `Intl` constructor: `undefined` means "whatever locale this browser
or OBS instance has" and produced mixed-language copy. Both wrappers default
to the active UI locale and cache their `Intl` constructors, so per-render
calls are fine. Most of the frontend is not yet migrated; move call sites
case by case depending on whether the value is UI copy or viewer data.

## The contributor tool (ADR-0063)

Beta testers translate at `/translate`, not by PR: request locale, admin
approves, contributor translates namespace by namespace (key list derived
from `enMessages` in the browser, placeholder parity checked live and
server-side), submissions sit in `localization_translations` (migration 097),
admins review at `/admin/localization`, and
`GET /api/v1/admin/localization/export/<locale>` gives the approved rows.
`scripts/generate-locale-catalog.mjs <export.json> --out <dir>` writes the
namespace files. Merge an export into `messages/de/` by hand rather than
regenerating it: regenerating overwrites each file whole and drops keys the
export lacks. The PR is the last gate.

## Adding another locale

1. Add the code to `SUPPORTED_LOCALES` and `LOCALE_NATIVE_NAMES` in `config.ts`.
2. Add `messages/<code>/`: hand-written files annotated
   `LocaleNamespace<'ns'>` (missing/extra key is a compile error) or
   generated files (partial, per-key English fallback); compose in
   `messages/<code>/index.ts` as `LocaleMessages`.
3. Add its loader to `catalogLoaders` in `active-locale.ts` (the only
   place mapping locale to catalog).
4. Add coverage/placeholder-parity tests like `__tests__/de.test.ts`, and
   check whether the language fits the one/other plural pairs.
5. The settings card and gate cover it automatically; the homepage switch
   lists every entry in `SUPPORTED_LOCALES` unfiltered, so gate any language
   that should stay in beta before it lands.

## Testing

Tests live in `frontend/src/lib/i18n/__tests__/`:

```bash
cd frontend && npx vitest --project unit --run src/lib/i18n/
```

Unit tests are only discovered under `__tests__/`; the `unit` project is
`environment: 'node'`, so a component test needs a
`// @vitest-environment jsdom` docblock. The `@ts-expect-error` in
`__tests__/translate.test.ts` is a gate: if `MessageKey` degrades to
`string`, `tsc --noEmit` fails on it as unused. Never `npm test` in
`frontend/`, it is bare `vitest` in watch mode. Every new file under
`src/lib/i18n/` needs the AGPL header block; nothing lints for it.
