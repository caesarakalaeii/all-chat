# Frontend i18n

All-Chat's UI strings live in a typed catalog at `frontend/src/lib/i18n/`.
English is the default and source locale; German is the second. A user picks
the language in the homepage nav or on `/settings`, the choice is stored per
browser, and the locale never appears in the URL.

The design and the alternatives that were rejected are in
[ADR-0055](../adr/0055-ui-string-catalog-without-locale-routing.md) (the
catalog), [ADR-0066](../adr/0066-client-side-ui-locale-selection.md) (how a
locale is chosen) and
[ADR-0078](../adr/0078-homepage-language-switch-and-german-for-everyone.md)
(the homepage switch). This guide is the practical part.

## The module

| File | Holds |
|---|---|
| `config.ts` | `SUPPORTED_LOCALES`, `Locale`, `DEFAULT_LOCALE`, `LOCALE_NATIVE_NAMES`, `isSupportedLocale` |
| `messages/en/<namespace>.ts` | one file per namespace, each a nested object literal ending in `as const` |
| `messages/en/index.ts` | the barrel that composes them into `enMessages` and `EnMessages` |
| `messages/de/` | the German catalog: one file per namespace typed `LocaleNamespace<'ns'>`, composed into `deMessages: LocaleMessages` |
| `translate.ts` | `translate`, `translateWithFallback`, `MessageKey`, `TFunction`, the `Locale*` catalog types |
| `active-locale.ts` | the active locale (module state), catalog loaders, `restoreStoredLocale`, `chooseLocale` |
| `translators.ts` | locale to `TFunction`, cached per locale |
| `use-translations.ts` | `useTranslations`, `useActiveLocale` (`'use client'`) |
| `format.ts` | `formatNumber`, `formatDateTime` |
| `index.ts` | the barrel call sites import from |

No React Context, no store library, no request state, no dependency.

Importers write `./messages/en`, which resolves to the barrel. There is no
`messages/en.ts`.

## Which namespace

One file per namespace, all of them in `messages/en/`. Pick by the **surface** a
reader can point at, not by the component tree:

| Namespace | Surface |
|---|---|
| `a11y` | assistive-technology-only strings no sighted user reads |
| `admin` | the admin console, `src/app/admin/**` |
| `auth` | sign-in, the OAuth callback catchers, their error states |
| `blog` | the chrome around the engineering blog, `/blog` and `/blog/<slug>`; the posts themselves are not catalog strings (see "The lint gate") |
| `common` | a string genuinely shared by two or more surfaces |
| `dashboard` | the streamer dashboard and its widgets |
| `docs` | the in-app documentation pages |
| `errors` | chat error copy, keyed by `ChatErrorType`; backs `src/lib/errorMessages.ts` |
| `guides` | the public search-intent guides: `/obs-chat-overlay`, `/obs-chat-dock`, `/tiktok-live-chat-overlay`, `/multistream-chat`, `/compare`, and their table of contents at `/guides`, including their route metadata |
| `legal` | privacy, terms, and the Impressum's not-configured fallback |
| `maintenanceBanner` | the site-wide maintenance banner |
| `marketing` | the public homepage, the upgrade page, the device-link flow |
| `metadata` | route `export const metadata` — SEO titles and descriptions |
| `moderation` | the moderation queue and its actions |
| `onboarding` | the first-run tour |
| `overlayEditor` | the overlay editor: canvas, inspector, appearance, theme marketplace |
| `settings` | the settings surfaces, linked devices, platform connections |
| `translate` | the beta-tester localization contributor tool, `/translate` |
| `viewerOverlay` | viewer-facing overlay chrome — labels, buttons, empty states |

Adding a namespace means adding it to `EXPECTED_NAMESPACES` in
`src/lib/i18n/__tests__/messages.test.ts`, which is what stops two surfaces
inventing two names for the same thing.

`common.*` is not a dumping ground and not a first guess. Put a string in the
namespace of the surface that renders it, and move it to `common` when a **second**
surface reads the same string. A `common` key with one caller is copy nobody owns.

## Adding a string

1. Add the key to `frontend/src/lib/i18n/messages/en/<namespace>.ts`.
2. Add the German string at the same path in `messages/de/<namespace>.ts`.
   `tsc` fails until you do: each German namespace file is typed as the complete
   English shape. (`legal` is the exception, see "Locales".)
3. Read it at the call site.

The barrels need no edit unless the namespace itself is new.

**Server Components, plain modules and tests** use `getTranslations()`:

```tsx
import { getTranslations } from '@/lib/i18n'

export default function Page() {
  const t = getTranslations()
  return <h1>{t('a11y.skipToMainContent')}</h1>
}
```

**Client Components** use `useTranslations()`:

```tsx
'use client'
import { useTranslations } from '@/lib/i18n'

export function Banner({ title }: { title: string }) {
  const t = useTranslations()
  return <button aria-label={t('maintenanceBanner.dismissLabel', { title })}>…</button>
}
```

Both return a `TFunction` with the same signature. The difference is when the
locale is read: `useTranslations()` re-renders the component when the user
switches language, `getTranslations()` resolves the active locale on each call.
On the server the active locale is always English, so a Server Component
renders English whatever the user chose (see "Locales").

`t` keeps one identity for the life of the page, across language switches too,
so an effect that lists it never re-runs because of a switch. The flip side: a
`useMemo` keyed only on `t` keeps whatever copy it computed first. Resolve copy
during render instead of memoising it.

`t()` takes a dotted key, checked at compile time. A key that is not in the
catalog is a type error, so `npx tsc --noEmit` catches a typo before any test
runs.

## Namespace convention

- camelCase, nested **at most three levels**: `maintenanceBanner.dismissLabel`,
  not `components.banners.maintenance.dismiss.label`.
- Keyed by **surface**, not by component internals — the namespace names the
  screen or widget a reader can point at.
- `common.*` is for a string genuinely shared by two or more surfaces. Do not
  create it, or any other namespace, to hold a single key nobody else reads.
- Every namespace file ends in `as const`, and the barrel composes them by naming
  them in a literal object. This is load bearing: `MessageKey` is derived from the
  literal key types. Spreading, `satisfies MessageCatalog` or an explicit type
  annotation on `enMessages` would each widen it and silently turn the
  compile-time key check into `string`.

## Placeholders

Single braces, `{name}`, matching the convention already used in
`frontend/src/lib/errorMessages.ts`. Do not introduce a second syntax.

```ts
dismissLabel: 'Dismiss maintenance banner: {title}',
```

```ts
t('maintenanceBanner.dismissLabel', { title: 'Database upgrade' })
```

`params` is `Record<string, string | number>`. Every occurrence of a placeholder
is replaced, so `'{word} and {word}'` with `{ word: 'echo' }` gives
`'echo and echo'`.

There are no ICU plurals and no `select`. English and German share the same
one/other plural split, so the existing `…One` / `…Many` key pairs cover both.
When a language with other plural rules arrives, plurals go behind the same
`t()` signature, so the engine can be swapped without touching call sites.

A German string keeps exactly the placeholders of its English source;
`__tests__/de.test.ts` fails on a renamed or dropped one.

**Do not concatenate translated fragments to build a sentence.** Word order is
the first thing a second language changes. Put the whole sentence in one key with
placeholders in it.

## Lookup never throws

A key the active non-English catalog lacks resolves in English. A key English
lacks too resolves to the key string. A missing param leaves the
`{placeholder}` visible. The last two `console.warn` outside production.

That is deliberate, and it is the one rule not to "improve". Overlay pages render
inside OBS browser sources on live broadcasts. An exception raised from a string
lookup unmounts the tree, and the viewer sees a black overlay for the rest of the
stream. A visible key is obviously a bug and costs nobody their broadcast.

## The lint gate

`frontend/eslint.i18n.config.mjs` fails on a user-visible string written at its
render site. It runs in `.github/workflows/frontend-i18n.yml` as a required check.
Run it exactly as CI does:

```bash
cd frontend
npx eslint -c eslint.i18n.config.mjs \
  --suppressions-location eslint.i18n.suppressions.json \
  'src/**/*.tsx'
```

It catches two things:

- **JSX text nodes** — `<p>Hello</p>` — via `react/jsx-no-literals` with
  `noStrings: true`. Punctuation and symbols (`·`, `—`, `/`, `→`, …) are in
  `allowedStrings`, because they are not copy and a key per bullet is noise.
- **User-visible props** — `aria-label`, `placeholder`, `title`, `alt`, `label` —
  via a `no-restricted-syntax` selector. `alt=""` is exempt: an empty `alt` is the
  correct marker for a decorative image, not missing copy.

It deliberately says nothing about `className`, `href`, `type`, `id` or `data-*`.
Those are machine input, and flagging them buries the real hits.

Not linted: `src/stories/**` and `src/**/__tests__/**`. Both render JSX as input
to an assertion, so a catalog key there would only assert that it resolves to
itself. Also not linted: `src/content/blog/**`, the blog posts. They are dated,
first-person English prose rather than UI copy; in the catalog they would be
offered to `/translate`, and a translated copy of a dated post is a second version
nobody keeps in step. The blog's chrome in `src/app/blog` and
`src/components/blog` is linted like any other surface.

### The suppressions file

`frontend/eslint.i18n.suppressions.json` is an ESLint bulk-suppressions baseline.
It **only ever shrinks**. A new violation fails the build immediately; the file is
the record of what was already there when the gate landed.

After migrating strings out of a file, its suppressions go stale. Prune them:

```bash
cd frontend
npx eslint -c eslint.i18n.config.mjs \
  --suppressions-location eslint.i18n.suppressions.json \
  --prune-suppressions 'src/**/*.tsx'
```

Then commit the shrunken file. Never run `--suppress-all`: it re-adds whatever is
currently broken and silently turns the gate off for it.

There is no inline escape hatch. The config sets `noInlineConfig: true`, so an
`// eslint-disable-next-line` comment has no effect — by design, so the only way
to not fix a violation is a line in a file that a reviewer sees grow.

## Dates and numbers

Use `formatDateTime` and `formatNumber` from `@/lib/i18n` rather than
`toLocaleString()` or a bare `Intl` constructor.

```ts
import { formatDateTime } from '@/lib/i18n'

const DATE_OPTIONS: Intl.DateTimeFormatOptions = { month: 'short', day: 'numeric' }
formatDateTime(new Date(window.ends_at), DATE_OPTIONS)
```

Passing `undefined` as the locale — which is what `toLocaleString()` and
`new Intl.DateTimeFormat(undefined, …)` do — means "whatever locale the browser or
OBS instance happens to have". That made English copy render German month
abbreviations, and made the same banner read differently on two machines. These
wrappers default to the active UI locale instead: English for an English UI,
German (`1.234.567`, `4. März`) once a user picks German.

Both wrappers cache their `Intl` constructors, keyed by locale plus the serialised
options, so calling them per render is fine and you do not need a module-level
formatter constant.

Most of the frontend has **not** been migrated onto these yet: at the time of
writing there are still dozens of unpinned `toLocaleString()` / `Intl.*` call
sites. Each needs its own look at whether the value is UI copy or viewer data, so
they move over case by case rather than in a sweep.

## Why there is no provider

`useTranslations()` is hook-shaped but is not backed by a React Context.

- The frontend has **no React Context at all** —
  `grep -rn 'createContext\|useContext' frontend/src` returns nothing. State is
  Zustand or module singletons.
- Storybook renders components standalone, and `npx vitest --project storybook
  --run` is a required CI gate. A component that needs a wrapping provider to
  render would break it.

Instead the active locale is a module singleton in `active-locale.ts`, and the
hook subscribes to it with `useSyncExternalStore`. A component rendered without
anything around it, in Storybook or a test, simply renders English.

## Locales

| Code | Catalog | Coverage |
|---|---|---|
| `en` | `messages/en/` | the source; every key |
| `de` | `messages/de/` | every namespace except `legal`, machine-translated first |

How a locale reaches the screen (ADR-0066):

1. The server always renders `DEFAULT_LOCALE` (`en`). Nothing reads a cookie,
   header or account preference, so static pages stay static.
2. `components/LocaleSync.tsx`, in the root layout, runs `restoreStoredLocale()`
   after hydration. It reads `localStorage.allchat_locale`, fetches that catalog
   with a dynamic `import()`, and activates it: `<html lang>` changes and every
   `useTranslations()` subscriber re-renders.
3. The homepage nav switch (`components/home/LanguageToggle.tsx`) and the
   `/settings` language card call `chooseLocale()`, which does the same and
   stores the choice. No stored choice means English, never the browser's
   language: an OBS instance on a German machine must not switch an overlay on
   its own.

What that leaves English:

- **Server Components**, including their `metadata`: the homepage's metadata and
  JSON-LD, guides, docs, blog chrome, the legal pages and the root skip link.
  Their German strings exist and are unused until those surfaces resolve a
  locale on the client. The homepage body is `HomeClient` and its sections,
  which are client components, so it does switch.
- **Overlays in OBS.** A browser source has its own storage, so it is English
  unless someone picks a language inside it.
- **`legal.*`** in every surface, including the cookie banner. Binding text is
  not published in a language a lawyer has not read.
- **Strings resolved once at module load**, such as the editor's
  `EDITOR_LOADING_LABEL` constants: they are computed before any locale is active.

Who can pick a language other than English on `/settings` is the
`ui_languages` feature gate (migration 103), enforced by share-service on
`GET /api/v1/ui-languages`, which the settings card probes. It shipped
early-access and free, and is opened to everyone by turning `early_access` off
in the admin UI (ADR-0078). The homepage switch does not probe the gate:
signed-out visitors could never pass it. Closing the gate again therefore hides
German on `/settings` only.

The German catalog is not in the localization tool's database. Running
`scripts/generate-locale-catalog.mjs` on a `de` export overwrites each namespace
file whole and drops every key the export lacks, so merge an export into
`messages/de/` rather than regenerating it.

## Why locale is not in the URL

`/overlay/[id]` is pasted into OBS browser sources, shared links, the browser
extension and the Stream Deck plugins, and left there for months. A
`/[locale]/overlay/[id]` segment would invalidate every overlay that already
exists, silently and mid-broadcast. Public routes are also indexed unprefixed via
`src/app/sitemap.ts` and `src/app/robots.ts`.

This is a rule, not a current limitation: **locale never goes in the URL.**

## The contributor tool (ADR-0063)

Beta testers translate the catalog through a UI, not a PR: `/translate` (nav
link visible to beta testers and ambassadors). The pipeline:

1. A contributor requests a locale; an admin approves it (it then appears for
   every contributor).
2. The contributor picks a namespace and translates string by string — the
   key list is derived from `enMessages` in the browser, so the tool can never
   show a key the repo does not have. Placeholder parity is checked live and
   again server-side.
3. Submissions sit in `localization_translations` (migration 097) as one row
   per (locale, key); resubmitting overwrites and resets to `pending`.
4. Admins review at `/admin/localization`: approve, or request changes with a
   note the contributor sees.
5. `GET /api/v1/admin/localization/export/<locale>` downloads approved rows as
   JSON; `scripts/generate-locale-catalog.mjs` turns that into
   `messages/<locale>/<namespace>.ts` files plus a printed checklist of the
   wiring steps in "Adding another locale". The PR is the last gate — nothing
   auto-commits.

The `translate` namespace holds the tool's own strings and is deliberately
excluded from its own translation surface: the tool's copy is what a
contributor reads while learning the tool. The feature is gated by the
`localization_contribution` feature gate (early-access, migration 097), not by
premium: contribution is a role behavior, so `/upgrade` does not list it.

## What is not here

- Locale selection at request time — no `middleware.ts`, no `cookies()` or
  `headers()` read, no `Accept-Language` parsing, no account preference, no
  locale column. Reading request state in the root layout makes every page
  dynamic, including the static marketing and docs pages. See ADR-0066.
- `next-intl`, `react-intl`, `i18next`. See ADR-0055.
- `errorMessages.ts`. It is a `Record<ChatErrorType, …>` with `actionableSteps`
  arrays and gets its own migration.
- Overlay chat message and event rendering. Viewer-authored chat content is never
  translated.

## Adding another locale

1. Add the code to `SUPPORTED_LOCALES`, and its name written in that language to
   `LOCALE_NATIVE_NAMES`, in `config.ts`.
2. Add `messages/<code>/`. Hand-written namespace files are annotated
   `LocaleNamespace<'ns'>` so a missing or extra key is a compile error; files
   from `scripts/generate-locale-catalog.mjs` are partial and fall back to
   English per key. Compose them in `messages/<code>/index.ts` as
   `<code>Messages: LocaleMessages`, like `messages/de/index.ts`.
3. Add its loader to `catalogLoaders` in `active-locale.ts`, the only place
   that maps a locale to its catalog.
4. Add a coverage and placeholder-parity test like `__tests__/de.test.ts`.
5. Check the plural keys: the `…One` / `…Many` pairs only fit languages with a
   one/other split.
6. The settings card and the `ui_languages` gate cover the new language with
   no further change. The homepage switch lists every entry in
   `SUPPORTED_LOCALES` and is not gated, so a language that should stay in
   beta needs the switch filtered before it lands. Cover the Patreon post from
   CLAUDE.md's "Shipping a Feature".

## Testing

Tests live in `frontend/src/lib/i18n/__tests__/`. Run them with:

```bash
cd frontend && npx vitest --project unit --run src/lib/i18n/
```

Never `npm test` in `frontend/` — it maps to bare `vitest`, which is watch mode.

Unit tests are only discovered under a `__tests__` directory; a test file
anywhere else is silently never run. The `unit` project is `environment: 'node'`,
so a component test needs a `// @vitest-environment jsdom` docblock — see
`frontend/src/components/__tests__/MaintenanceBanner.test.tsx`.

The `@ts-expect-error` line in `__tests__/translate.test.ts` is a gate, not a
comment: `tsconfig.json` type checks test files, so if `MessageKey` degrades to
`string` the suppression becomes unused and `tsc --noEmit` fails. Do not delete
it.

`__tests__/index.test.tsx` covers switching (subscribers re-render, effects do
not re-run, `<html lang>`, formatters, the English fallback, the stored choice)
and runs under jsdom.
`__tests__/de.test.ts` pins which namespaces German covers and that every German
string keeps its English placeholders.

Every new file under `src/lib/i18n/` needs the AGPL header block. Nothing lints
for it.
