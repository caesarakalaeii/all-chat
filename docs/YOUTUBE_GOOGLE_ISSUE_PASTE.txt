DESCRIPTION:
============

YouTube Live Chat API liveChatMessages.streamList gRPC endpoint consistently closes connections after exactly 10 seconds, despite documentation describing it as a "server-streaming connection" that is "the most efficient way to consume live chat messages."

This makes the API unusable for production: 6 reconnects/min × 5 quota = 1,800 units/hour per stream = 43,200 units/day. With 10K daily quota, can only support 0.23 streams.

We've tested exhaustively:
✅ Removed pageToken on initial connection
✅ Aggressive gRPC keepalive (5s ping interval)
✅ Increased flow control window (4MB)
✅ Async message processing
✅ Matched Python demo parameters (maxResults=20)
✅ Removed maxResults entirely
✅ Multiple channels (high/low activity)

Result: ALL configurations close at exactly 10 seconds with io.EOF.

Pattern observed:
1. Connect to streamList
2. Receive 15-20 responses over 10 seconds
3. Receive empty response (0 messages, duplicate pageToken)
4. Stream closes with EOF
5. Must reconnect → repeat

Expected: Streams lasting hours (as documentation implies), consuming ~5 units for initial connection + negligible maintenance cost.


API REQUEST WITH PARAMETERS:
============================

gRPC Proto: V3DataLiveChatMessageService.StreamList()

Request:
{
  "live_chat_id": "Cg0KC3pTT2F3ZWNXc1B3KicKGFVDOHJjRUJ6SlNsZVRrZl8tYWdQTTIwZxILelNPYXdlY1dzUHc",
  "part": ["snippet"],
  // maxResults omitted (tested with 20, 200, 2000 - no difference)
}

gRPC Connection Settings:
- Keepalive: 5s ping interval, 2s timeout
- Flow control window: 4MB initial
- TLS enabled
- Endpoint: youtube.googleapis.com:443
- Auth: OAuth2 Bearer token

EXPECTED RESULT:
================

Per documentation: "server-streaming connection that pushes new messages as soon as they are available" and is "the most efficient way to consume live chat messages"

Expected:
- Stream duration: Minutes to hours (until livestream ends or network error)
- Quota consumption: ~5 units for initial connection + negligible maintenance
- Reconnections: Only on errors, not every 10 seconds
- Production viability: 1,000+ concurrent streams with reasonable quota

Production implementations report streams lasting "hours" with proper keepalive. We cannot achieve this despite following best practices.

Question: Is the Python demo's "while True" loop present because streams are DESIGNED to close every 10s? If so, documentation is misleading about efficiency.
